# Post-1.0 Improvement Plan

**Date:** 2026-08-06
**Status:** Proposed
**Scope:** Engineering improvements only — operational assurance, minimal observability, small
hardening items, and the two scheduled performance tracks. No user-facing feature work: features
enter their own plans when users ask for them. This plan turns ADR 0063's risk-acceptance backlog
into ordered, gated stages, and records the explicitly trigger-based items so nothing deferred is
ambient.

**Owner decisions incorporated (2026-08-06):** engineering-only scope; observability starts
minimal (full OpenTelemetry stays trigger-based); multi-instance stays deferred behind its
existing blocked plan; both performance tracks (cost-engine computation and the PostgreSQL
column-type work) are scheduled actively.

## 1. Context

1.0 shipped with every delivery gate accepted (ADRs 0025/0026/0027/0063) and six documented risk
acceptances (ADR 0063 §"Risk acceptances"). Two of those carry commitments this plan discharges
(the restore rehearsal; the deferred environment-level security tests), one is a capability gap
this plan narrows (observability), and the rest are trigger-based and stay that way. Separately,
the 2026-08-06 cost-read materialisation plan closed its own scope but surfaced a measured
computation-cost finding in the cost engine that was explicitly left "for a future plan" — this is
that plan.

House rules apply throughout: TDD (failing test first), the commit gate, PostgreSQL as the
performance-priority provider with SQLite kept correct via the shared contract suites but not
measured, and no test whose subject is the test harness.

## 2. Ordered stages

Stages are dependency-light and mostly independent; the order below is priority order. Stage 1 is
calendar-bound (ADR 0063 item 6); everything else is sequenced by value.

### Stage 1 — Production restore rehearsal (ADR 0063 item 6)

The committed close-out of the last §9.4 deferral with a deadline: within the first operational
quarter, before the database accumulates irreplaceable history.

1. Provision a disposable Cloud SQL instance from a production automated backup (not a fresh
   schema deploy — the point is exercising the real backup artefact).
2. Point a staged Cloud Run revision (zero traffic) at the restored instance; run the
   `tests/hurl/` smoke suite against it.
3. Rehearse point-in-time recovery to a timestamp between two known writes and verify the second
   write is absent.
4. Record measured RPO/RTO figures and the procedure as
   `docs/operations/cloud-sql-restore-rehearsal.md`; link it from ADR 0063 item 6 as closed.

**Acceptance:** the runbook exists with measured figures; ADR 0063 item 6 is marked discharged.
No product code changes — no product tests. This is deliberately an operations rehearsal, not a
new automated suite: the automated `TC-DB-BACKUP-001` smoke test already covers the repeatable
part.

### Stage 2 — Minimal observability

The smallest set that makes a production incident diagnosable and noticed, per the owner's
decision. Full §9.2 OpenTelemetry is *not* this stage — see §3.

1. **Health endpoint.** `/healthz` via `MapHealthChecks`, with a database-touching check through
   the existing keyed data sources (a `SELECT 1`-class probe on the domain connection — not
   `IJobTrackClient`, which would entangle health with authorization). Anonymous but
   information-free: status code only, no version/provider/config detail in the body. Wire it as
   the Cloud Run startup/liveness probe and the deploy script's candidate smoke check (replacing
   the current page-scrape `curl`). TDD: integration tests for healthy, database-down (503), and
   response-body austerity; architecture test adding `/healthz` to the anonymous-surface
   inventory.
2. **Request/operation logging with correlation.** Every `IJobTrackClient` call already carries a
   correlation context; ensure the web host logs one structured line per state-changing operation
   (operation name, actor ID, correlation ID, outcome, duration) and that unhandled-exception
   logs carry the same correlation ID. Redaction rules from §9.2 apply now, not later: no rates,
   costs, credentials, tokens. TDD: a logging-assertion test per representative handler shape,
   plus a negative test proving a rate/cost value never reaches a log line.
3. **Alerting on built-ins.** Cloud Monitoring alert policies (scripted in the deploy script, so
   they are provisioned idempotently like everything else): 5xx rate, p95 latency, instance
   restart loops, Cloud SQL disk/connection saturation, failed Cloud SQL backups. Document the
   policies and their intended response in `docs/operations/monitoring-and-alerts.md`.

**Acceptance:** probes and smoke test use `/healthz`; the three test groups pass on both
providers where provider-relevant; alert policies exist in the deploy script and are documented.

### Stage 3 — Small hardening items

Batched one-day items, each already identified in review:

1. HSTS `max-age` to one year (`Program.cs`; remove the scaffold comment). Decide `preload`
   explicitly — likely no for an internal host — and record the decision inline.
2. Native service-host integration is **not** done here: it belongs to the ADR 0014 self-hosted
   topology only and stays trigger-based (see §3) now that ADR 0062 fixes production on Cloud
   Run.

**Acceptance:** `-warnaserror` build and the web integration suite pass; the HSTS value is
asserted by the existing security-headers test (extend it if it does not yet pin `max-age`).

### Stage 4 — Cost-engine computation cost (the 2026-08-06 recorded finding)

The measured hotspot: with materialisation fixed, `CostSegmentPartitioner`/`CostEngine`
per-worker computation is the dominant term at long-history session density — ~359–508 ms
(partition + calculate across 20 workers' ~36,500 sessions), leaving leaf reads at ~608–670 ms
and branch reads at ~721–745 ms against original aspirations of 150 ms/2 s. The long-history
ceilings were honestly revised to 900 ms/1 s pending this work
(`performance-budgets.md` §4 revision policy).

1. **Profile before changing anything** (house discipline: budgets before tuning, plan §9.3).
   Attribute the ~360–500 ms between partitioning, allocation-share arithmetic, and interval
   algebra at the measured density; record the attribution in `performance-budgets.md`.
2. Pursue algorithmic wins in the pure engine first — the partitioner and engine are
   provider-neutral domain code, so improvements land for both providers and stay inside the
   exact-rational arithmetic rules (no `double` on the duration/money path, ADR 0002
   reconciliation untouched). Candidate shapes to evaluate against the profile, not
   presupposed: partition-boundary event sweeps instead of per-session scans, memoised
   per-worker segment maps, and avoiding rework across the per-worker loop.
3. **No PostgreSQL-only cost algorithm** unless differential tests prove it equivalent to the
   pure engine and SQLite remains conformant (plan §9.3's standing rule) — the strong default is
   that this stage never leaves the domain layer.
4. TDD: the existing engine correctness suites (including the concurrency-splitting and
   largest-remainder reconciliation tests) must pass unchanged — they are the specification.
   New tests only for any new pure functions introduced.
5. Re-measure the long-history lane; tighten `LongHistoryScalePerformanceTests` ceilings to the
   new measured capability with real headroom, per the §4 revision policy. Target: restore the
   original 150 ms leaf aspiration if the profile shows it is reachable; otherwise record why
   and set the honest number.

**Acceptance:** attribution recorded; correctness suites pass unchanged; ceilings tightened (not
loosened) with re-measured evidence; `./scripts/perf-test.sh` green.

### Stage 5 — PostgreSQL column-type and index optimizations

Activates `2026-07-11-postgresql-column-type-remediation-plan.md` (currently Proposed, deferred
post-1.0) as the authoritative spec for this stage — this plan does not restate its content. Two
sequencing constraints now bind that the older plan predates:

1. **ADR 0011 is now binding**: every schema change is a new forward-only versioned script,
   compatible with the revision serving traffic (expand/contract, per the Cloud Run runbook's
   schema-upgrade contract). The older plan's in-place editing assumption is superseded.
2. Stage 4 first: engine computation is the measured dominant term, so column-type work is
   evaluated against post-Stage-4 profiles — any item in that plan that no longer pays for
   itself under the new profile is withdrawn with evidence rather than executed on momentum.

Update the older plan's status block when this stage starts and finishes; keep the plans index in
step.

**Acceptance:** per the older plan's own acceptance checks, plus dual-provider contract suites
green (SQLite functionally conformant, unmeasured) and perf-lane evidence for each schema change
that claims a win.

### Stage 6 — Deferred environment-level security test evidence (ADR 0063 item 5)

Closes the two evidence gaps from the 2026-08-01 audit. Low urgency: both guard behaviour that
unit tests already prove at the abstraction level.

1. **Live TLS against a real trusted CA:** a gated integration test (opt-in environment
   variable, like the existing real-PostgreSQL lanes) that connects to a TLS-terminated
   PostgreSQL endpoint with full chain validation, proving the fail-closed path against a real
   handshake rather than validator options.
2. **Process-level argv/stdout inspection:** a gated test that launches the actual
   `JobTrack.Database`/`AdminCli` binaries and inspects the OS process table and captured stdout
   for secret material, proving the abstraction-level rejection tests hold end-to-end.

**Acceptance:** both tests exist, run in their gated lanes, pass; ADR 0063 item 5 marked
discharged.

## 4. Delivery discipline

- One stage per commit series; the commit gate (`-warnaserror` build, `dotnet format`,
  `fast-test.sh`, targeted `--filter`) after every slice; full `all-test.sh` at each stage's
  close, per house rules — not mid-stage.
- Stages 4 and 5 are perf work: every claim lands as a measured figure in
  `performance-budgets.md` with the enforcing test named, or it does not land.
- Update this plan's status block per stage (`Stage N done — date`), and the plans index row with
  it. ADR 0063's discharged items get a one-line annotation pointing here rather than an edit to
  their original text.

## 5. Completion criteria

This plan is complete when Stages 1–6 are done (or individually withdrawn with recorded
evidence), the trigger register above has migrated into whatever plan supersedes this one for
items whose triggers fired, and ADR 0063 items 5 and 6 are annotated as discharged.
